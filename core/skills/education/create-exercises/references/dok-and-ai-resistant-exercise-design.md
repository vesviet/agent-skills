# Depth of Knowledge (DOK 1-4) & AI-Resistant Exercise Design

This reference guide details Webb's Depth of Knowledge (DOK) cognitive framework and provides concrete architectural specifications for designing exercises resilient against superficial AI generation and copy-paste outsourcing in 2026–2027 educational environments.

---

## 1. Webb's Depth of Knowledge (DOK) Cognitive Matrix

Webb's Depth of Knowledge categorizes tasks by the cognitive complexity required to complete them, rather than difficulty alone. A task may be difficult yet cognitively shallow (e.g., memorizing 100 historical dates), or cognitively deep while accessible (e.g., comparing two design approaches).

| DOK Level | Cognitive Focus | Cognitive Verbs | Assessment Objectives | Sample Computer Science & Engineering Task |
|---|---|---|---|---|
| **DOK 1: Recall & Reproduction** | Retrieval of specific facts, definitions, syntax, or single-step algorithmic execution. | *Recall, Define, Identify, State, Calculate, Recognize* | Verify baseline factual accuracy and rote familiarity with foundational terminology and standard library signatures. | "State the time complexity of lookup in a balanced red-black tree, and write the standard syntax for declaring a buffered channel in Go." |
| **DOK 2: Skills & Concepts** | Application of conceptual understanding, two-or-more-step decision rules, comparisons, and structured problem solving. | *Classify, Compare, Organize, Construct, Modify, Predict* | Assess ability to translate concepts into standard implementations, transform data structures, or follow established patterns. | "Compare optimistic locking with pessimistic locking in a relational database. Modify the provided transaction function to apply an exponential backoff retry loop." |
| **DOK 3: Strategic Thinking** | Non-routine reasoning, planning, evidentiary justification, handling trade-offs with multiple viable solutions. | *Analyze, Critique, Formulate, Hypothesize, Justify, Debug* | Require learners to diagnose complex failures, justify architectural trade-offs, and defend design decisions against constraints. | "Analyze the provided distributed order service trace logs exhibiting intermittent 504 Gateway Timeouts. Formulate a hypothesis for the root cause, and implement an automated reproduction test proving the connection leak." |
| **DOK 4: Extended Thinking** | Sustained synthesis, cross-domain integration, multi-stage project execution, and reconciliation of contradictory constraints. | *Synthesize, Design, Architect, Connect, Create, Prove* | Engage learners in end-to-end system design, evolutionary refactoring across multiple service boundaries, or formal verification. | "Design and implement a multi-region Raft replication engine capable of surviving arbitrary network partitions. Evaluate throughput vs consistency trade-offs, and prove safety using formal TLA+ specifications or Chaos Mesh injection." |

### Cognitive Distribution Rule
In 2026–2027 curricula, exercise sets must balance cognitive depth:
- **Introductory Modules**: 30% DOK 1, 40% DOK 2, 30% DOK 3.
- **Intermediate Modules**: 15% DOK 1, 35% DOK 2, 40% DOK 3, 10% DOK 4.
- **Advanced / Professional Modules**: 10% DOK 2, 50% DOK 3, 40% DOK 4 (0% isolated DOK 1).

## 2. The 5 AI-Shortcut Resistance Archetypes

Generative AI models excel at solving isolated, canonical textbook exercises (e.g., "Implement Dijkstra's algorithm" or "Explain ACID properties"). To ensure students develop genuine engineering intuition, exercise authors must employ five adversarial resistance archetypes.

### Archetype 1: Context-Bound Case Studies
Embed proprietary, fictitious enterprise constraints, legacy technical debt, and contradictory stakeholder requirements that cannot be solved by generic web training data.
- **Design Pattern**:
  - Invent a concrete organization, proprietary protocol, or internal legacy system (e.g., "MegaLogistics v2 legacy binary framing").
  - Introduce mutually conflicting constraints (e.g., "Must remain strictly backward-compatible with 2018 TCP client frames while reducing p99 latency below 12ms under 85% memory pressure").
  - Prohibit external library solutions where bespoke memory allocators or zero-copy parsers are required.
- **Why LLMs Fail**: Standard LLM outputs offer generic best practices (e.g., "Use Redis cache") that directly violate the specified legacy binary constraints or memory envelopes.

### Archetype 2: Synthetic Flaw & Hallucination Injection
Provide learners with a synthetically generated AI output containing subtle, realistic flaws (race conditions, off-by-one boundary leaks, goroutine leaks, or security vulnerabilities).
- **Design Pattern**:
  - Present a seemingly functional code snippet generated by an LLM with high superficial fluency.
  - Require the student to write an automated, deterministic test that consistently reproduces the failure.
  - Require the student to refactor the code to eliminate the flaw without breaking existing invariants.
- **Sample Exercise**:
  ```go
  // Task: The following token bucket rate-limiter was generated by an AI assistant.
  // It passes single-threaded unit tests, but fails intermittently in high-throughput clusters.
  // 1. Author an adversarial concurrent test case that triggers a race condition.
  // 2. Identify the exact line of the synchronization defect.
  // 3. Submit the minimal atomic fix using sync/atomic or mutex primitives.
  ```

### Archetype 3: Artifact-Grounded Inquiries
Require students to inspect and interpret raw, multi-modal operational telemetry rather than synthesized text prompts.
- **Design Pattern**:
  - Supply raw artifacts: OpenTelemetry distributed trace spans (JSON), Linux `perf` or Go `pprof` CPU flame graphs, PostgreSQL `EXPLAIN (ANALYZE, BUFFERS)` execution plans, or GC pause logs.
  - Ask targeted diagnostic questions anchored directly in the artifact data.
  - Task: "Identify which join node caused buffer spills to temporary disk files, and calculate the exact I/O overhead from the raw plan nodes."
- **Why LLMs Fail**: Without extensive bespoke OCR or multi-page context parsing, generic LLM prompts struggle to accurately extract exact line references and calculate specific byte offsets from raw telemetry dumps.

### Archetype 4: Socratic Oral Defense Simulation
Incorporate conversational defense checkpoints where learners must defend design trade-offs and runtime complexities against an adversarial AI sparring partner.
- **Design Pattern**:
  - Student submits an architecture proposal or pull request.
  - A sparring agent reviews the submission and generates targeted, challenging Socratic questions:
    - *"Why did you choose an LSM-tree storage engine over a B+ tree for this write-heavy time-series workload?"*
    - *"What failure mode occurs if node B partitions immediately after the leader receives quorum acknowledgment?"*
  - The learner must verbally or interactively defend their design choices, explaining the trade-offs considered and rejected.

### Archetype 5: Intermediate Process Audit
Shift assessment from final artifact evaluation to the verification of intermediate engineering processes and deliberate practice.
- **Design Pattern**:
  - Require learners to submit a structured git commit history showing iterative Red-Green-Refactor cycles.
  - Enforce inclusion of an engineering scratchpad (`THOUGHTS.md` or design journal) documenting:
    - Initial assumptions and mental models.
    - Hypotheses tested and falsified.
    - Benchmark comparisons between alternative data structures.
  - Submissions presenting a single monolithic commit with fully formed, perfect code without intermediate iterations are flagged for verification review.

## 3. Exercise Construction Blueprint & Quality Gates

When creating exercises, instructors and AI agents must follow this structured specification template:

```markdown
### Exercise Metadata
- **ID**: EX-2027-DIST-042
- **Topic**: Distributed Transaction Coordination & 2PC Failure Modes
- **Webb's DOK Level**: DOK 3 (Strategic Thinking)
- **Target Bloom Level**: Analyze & Evaluate
- **AI-Resistance Archetype**: Archetype 2 (Synthetic Flaw Injection) + Archetype 1 (Context-Bound)
- **Calibrated Difficulty ($\beta$)**: 0.75 (Intermediate-Advanced)

### Problem Statement & Scenario
[Fictitious enterprise context detailing legacy coordinator timeout behavior]

### Artifact Provided
[Seemingly correct Go implementation of Two-Phase Commit coordinator]

### Learner Deliverables
1. Automated reproduction test (`repro_partition_test.go`) triggering coordinator hang during prepare phase.
2. Root cause diagnosis citing exact line numbers in provided artifact.
3. Minimal non-blocking patch implementing epoch-based timeout abort.
4. Process scratchpad documenting debugging iterations.

### Human Review Gate
- Reviewer: [Educator Name & ID]
- Verification Status: [Approved for Cohort Deployment]
```

### Review Verification Invariants
1. **No Rote Trivialities**: Exercises claiming DOK 3 or DOK 4 must never reduce to simple syntax retrieval or standard API invocations.
2. **Contextual Grounding**: Problem statements must contain at least two domain-specific constraints preventing generic web scraping.
3. **Reproducible Testability**: Any debugging exercise must be accompanied by an automated test harness that deterministically validates the fix.
