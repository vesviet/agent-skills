# Scaffold New Service

Use this skill when a repo needs a brand-new service, worker, or similar bounded component.

## When to Use

- creating a new service, worker, or deployable unit
- bootstrapping from repo-local templates
- no fixed framework/layout assumed
- standing up a bounded component

## Core Rules

- start from the repo's template or nearest valid example
- keep the first version intentionally small
- define ownership and boundaries before adding features
- do not invent structure when the repo already has conventions
- leave the new service ready for tests, docs, and delivery wiring
- wire baseline observability (health endpoint, structured OTel spans on integration points) from the first commit
- if any code in this change was AI-generated, validate it per the risk tier defined in the backend-developer role before accepting

### 2025-2026: AI-Scaffolded Service Review

When scaffolding is assisted or fully generated by AI tools (Copilot Workspace, Cursor, Claude), apply the following review before treating the scaffold as valid:

- **Hallucinated dependency check:** verify every imported package, module path, and third-party dependency exists in the package registry and is pinned to a real version — AI scaffolding tools frequently invent plausible-sounding but non-existent package names.
- **Boundary completeness check:** confirm the scaffolded service has clearly defined inputs (API/event contract), outputs (response/event schema), and failure modes — AI-generated services often omit error handling and timeout contracts.
- **Environment binding check:** verify all generated environment variables, secrets, and service bindings are declared in the deployment config and documented in the README — do not deploy a service that silently requires undocumented env vars.
- **Observability gate:** confirm the generated service emits structured logs, at least one health/readiness endpoint, and an OTel span on its primary integration boundary — AI scaffolding rarely includes observability by default.
- **Security baseline:** check that generated auth middleware, input validation, and CORS config match the repo's existing patterns — AI-generated security code frequently uses permissive defaults.

## Suggested Process

### 1. Clarify The Service Boundary

Define:

- what the service owns
- what it exposes
- what it depends on
- what data it manages

### 2. Pick The Best Starting Template

Prefer:

- official scaffold command
- repo template
- nearby service with the same shape

Rename paths, identifiers, and generated artifacts carefully if copying.

### 3. Create The Minimum Structure

Add only what the repo expects, such as:

- entrypoints
- contracts
- core logic
- persistence
- config
- tests
- docs

### 4. Wire The First End-To-End Flow

Set up one narrow path that proves the service shape works:

- one entrypoint
- one use case
- one persistence or dependency path
- one health or readiness path if needed

### 5. Add Basic Verification

Use skill: `write-tests`

At minimum, add:

- one happy path
- one failure or validation path
- build and startup verification

### 6. Prepare Delivery Handoff

Use skill: `setup-deployment` if delivery config is needed.

Make sure the new service has:

- docs or README starter content
- basic ownership metadata if the repo uses it
- local verification steps

## Checklist

- [ ] service boundary defined
- [ ] local template or example chosen
- [ ] identifiers renamed safely
- [ ] minimum structure created
- [ ] first end-to-end flow wired
- [ ] baseline observability wired (health endpoint, OTel spans)
- [ ] tests added
- [ ] delivery handoff prepared
